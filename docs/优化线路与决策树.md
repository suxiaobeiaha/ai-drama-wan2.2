# 小说 → 视频流水线:优化线路与决策树

> 本文档记录本项目的优化路线图和所有关键技术决策(含原因与备选)。
> 更新方式:告诉 Claude"更新决策树",说明发生了什么变化即可。
> 最后更新:2026-10-15

---

## 一、项目定位

输入:小说文本(txt)→ 输出:带旁白的动画短片(mp4)

核心链路:
```
小说 → [Lumen 14B 快写] 改编方向(3选1) → 分镜梗概 → 逐镜草稿
     → [qwen3.6 27B 精修] 逐镜重写润色(策略二,当前暂跳)
     → [Wan 2.2 TI2V-5B] 逐镜生成视频(720p×121帧,首镜定角色图,后续图生视频)
     → [Windows TTS] 逐镜旁白配音 → [ffmpeg] 混音拼接 → 成片
```

## 二、决策树(已定决策 + 原因 + 备选)

### D1. 视频生成模型:Wan 2.2 TI2V-5B ✅
- **选择**:Wan 2.2 TI2V-5B(5B,48通道潜空间,需要 wan2.2_vae)
- **原因**:16GB 显存能跑;MiniMax H3(33B)在 AMD 卡上不现实
- **备选**:MiniMax H3(放弃,33B 太大+AMD 支持差)、Wan 2.2 A14B(16GB 卡可跑 fp8 版但慢,质量上限更高——想升级画质时重新评估)
- **关键知识**:TI2V-5B 输入输出都是 48 通道@/16 压缩,必须用 Wan22ImageToVideoLatent 节点 + wan2.2_vae(1.4GB),不是 wan_2.1_vae

### D2. 推理后端:原生 ROCm ✅
- **选择**:原生 ROCm(PyTorch 2.9.1+rocm7.2.1,直接装进 python_embeded)
- **原因**:DirectML 不支持 FP8/GGUF、易 OOM;venv 在嵌入式 Python 上 `python -m pip` 段错误(platformdirs ctypes 崩溃)
- **备选**:DirectML(放弃)、venv(放弃,段错误)、ZLUDA(未试,需求不存在)

### D3. 模型下载源:ModelScope 镜像 ✅
- **选择**:ModelScope(`Comfy-Org/Wan_2.2_ComfyUI_Repackaged` 全文件镜像)
- **实测速度**:每文件 8 连接 ≈ 4.5MB/s(两文件并行合计 ~9MB/s);hf-mirror 只有 ~0.7MB/s(xet US 桥接慢)
- **工具**:自研 parget.sh(8 连接分段+断点续传+实例锁;注意 curl 8.12 拒绝 -C 与 -r 混用)

### D4. 编剧模型:14B+27B 组合拳 ✅(策略一+二)
- **选择**:Lumen 14B(qwen2.5 创意写作特化)做快写(方向/梗概/草稿);qwen3.6 27B(IQ1_M)做精修(关键段生成/重写)
- **原因**:
  - 27B 质量高但 9.5 tok/s、长输出随机空响应/截断(IQ1_M 量化 + ROCm 组合缺陷)
  - 14B 快且稳,但对复杂嵌套 JSON schema 会吐空 `{}` → 用扁平字符串 schema(实测有效)
  - 27B 重写(锁结构)比续写快且质量提升明显(策略二)
- **规避手段(必读)**:
  1. 27B/14B 每次请求后 `keep_alive: 0` 强制卸载,下次全新加载(空响应基本消失)
  2. 27B 是思考模型,思考阶段吃 token——长任务用 14B,27B 只做短输出活
  3. JSON 输出只用扁平 schema(字符串字段,不嵌套对象数组)
- **备选**:纯 27B(慢+翻车)、纯 8B(llama3.1 写中文剧本质量不足)、纯 Lumen(快但细节糙)

### D5. LLM 与视频生成的 GPU 排他 ✅
- **选择**:流水线内置 stop_comfy()/start_comfy(),LLM 阶段与视频阶段互斥
- **原因**:实测两个 HIP 进程同时占 GPU 会死锁(Ollama 卡死不加载模型)
- **注意**:ComfyUI 空闲驻留 ~3.5GB 显存,足以卡死 16GB 的 LLM 加载

### D6. 视频规格:720p×121 帧(5秒)✅ 当前标准
- **选择**:1280×704 × 121 帧 @24fps(≈5秒/镜)
- **原因**:旁白(20-25字)需要 ~5 秒时长;720p 是 5B 模型合理画质上限
- **演进记录**:480×832×33(冒烟测试)→ 480×832×49(第一版成片)→ 720p×121(当前)
- **代价**:每镜约 8-10 分钟(含每镜重启服务器 ~40s + 模型加载 ~30s)
- **关键**:普通 VAEDecode 在 720p×61 帧就 OOM(单次 18.56GB 分配),必须 VAEDecodeTiled(256/64/32/4)

### D7. "每镜重启服务器" 规避 ✅(最重要的坑)
- **选择**:每生成一个镜头,重启 ComfyUI 进程
- **原因**:ROCm 下同一服务器进程内第二个及以后的生成产出单帧坏结果(原因未明,30 秒"假成功")
- **成本**:每镜多 ~40 秒 + 模型重新加载 ~30 秒
- **未解之谜**:根因待查(疑似 ROCm 运行时状态污染)。若未来修复,去掉此规避可提速 ~15%

### D8. 角色一致性:首镜定角色 + 图生视频 ✅
- **选择**:第一镜文生视频 → 提取首帧存 char_ref.png → 后续所有镜头用 Wan22ImageToVideoLatent 的 start_image 图生视频
- **原因**:独立文生视频的人物长相各镜不同;参考图锁定形象
- **局限**:起始图会锚定画面内容(动作起点同帧),可能限制运动幅度——观察成片效果再决定是否调整(备选:多参考图、LoRA 角色训练)

### D9. 旁白:Windows SAPI TTS ✅
- **选择**:System.Speech 中文语音,语速 Rate=2,wav→aac 后 ffmpeg `-shortest` 混入
- **原因**:零成本、离线、中文可用
- **备选**:更好的 TTS(edge-tts 音色好但需联网)、PaddleSpeech 等——音色不满意再换

### D11. 画质路线:Seedance 2.0 对比结论 ⏳ 待决策(2026-10-17 记录)
- **结论**:本地 16GB 显卡**无法达到** Seedance 2.0(即梦)级别。差距是代际的:商业模型(数据中心算力、双分支 DiT、1080p-2K、4-15秒/次、原生音效、Elo 榜第一)vs 本地 Wan 2.2 TI2V-5B(5B、720p、5秒/镜)。工程调优无法弥补
- **分层现实**:①静态图(SDXL 1024×1536)已接近主流 AI 绘画水平 ✅;②视频质量天花板卡在模型 ❌
- **三条路径(制片人待选)**:
  1. 本地升级:HunyuanVideo-1.5(腾讯开源,16GB 可跑,720p,物理规律更好,下载 ~15GB)——画质上一档,仍不及商业模型
  2. **混合方案(推荐)**:本地保留剧本/导演/资产/TTS 体系,视频环节做成可插拔引擎,成片质量需求时同一套剧本喂即梦 API(几毛钱/条)
  3. 云 GPU 跑更大开源模型(24GB+,成本高)
- **决策状态**(2026-10-21 更新):制片人已拍板走混合方案(即梦 API),引擎适配层已完成(settings 视频引擎=comfyui/jimeng 开关)。接入门槛调研:官方方舟 200 元起充(按量扣费,约2.3元/条720p,一片≈30元,余额长期有效,开通期低于200不可提现);第三方中转最低$1但非官方有风险。制片人正在权衡充值方式

### D10. 断点续跑与产物管理 ✅
- state.json(镜头完成列表)、script_plan.json(梗概规划)、directions.json(改编方向)、script.json 逐镜增量落盘
- 注意:改规格/改剧本后必须清掉旧 clip_*.mp4 等缓存产物,否则 concat 会复用旧片段
