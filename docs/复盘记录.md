## M0:环境搭建

### 问题 1:模型选型——MiniMax H3 不可行
- **现象**:想部署 MiniMax H3(33B 视频模型),评估后无法在 16GB AMD 卡上跑
- **分叉点 ⚡**:MiniMax H3 vs Wan 2.2 → **选 Wan 2.2 TI2V-5B**(5B,48通道潜空间,16GB 可跑)
- **关键知识**:TI2V-5B 必须配 Wan22ImageToVideoLatent 节点 + wan2.2_vae(1.4GB),用 wan_2.1_vae 会 48vs16 通道报错

### 问题 2:推理后端——DirectML 是死路
- **现象**:DirectML 不支持 FP8/GGUF、易 OOM
- **分叉点 ⚡**:DirectML vs 原生 ROCm vs ZLUDA → **选原生 ROCm**(torch 2.9.1+rocm7.2.1 直装 python_embeded)
- **解法**:不建 venv(嵌入式 Python 上 venv 的 `python -m pip` 段错误,platformdirs ctypes 崩溃)

### 问题 3:国内下载
- **现象**:hf-mirror 0.7MB/s(xet US 桥接);GitHub 直连被墙
- **解法**:ModelScope 镜像 4.5MB/s/文件;gh-proxy 走 GitHub
- **教训**:自研 parget.sh 踩坑史——curl 8.12 拒绝 `-C` 与 `-r` 混用(改用"失败分段整段重下");`(cmd &)` 子壳产生 135 个孤儿 curl 互相抢文件+拖垮网络(改 PID 跟踪+实例锁)

### 问题 4:720p 解码 OOM
- **现象**:720p×61 帧普通 VAEDecode 单次分配 18.56GB 超整卡
- **解法**:VAEDecodeTiled(tile 256 / overlap 64 / temporal 32/4)
- **知识**:帧数必须 4n+1(33/49/61/81/121),60 不合法

## M1:首版成片

### 问题 5:ROCm 二镜诅咒 ⭐ 本机最诡异的问题
- **现象**:同一 ComfyUI 进程内,第一个镜头正常(4分钟/49帧),第二个起 30 秒"假成功"产出**单帧**结果
- **排查**:整图缓存命中假象→全新服务器复现→确认规律"每进程只有首生成正常"
- **解法**:每镜重启 ComfyUI(代价每镜 +40 秒)
- **遗留**:根因未明,疑似 ROCm 运行时状态污染,列入技术债

### 问题 6:27B 空响应与截断
- **现象**:qwen3.6(IQ1_M 量化)长输出随机返回空/截断(截断点随机)
- **当时的解法**:每次请求后 keep_alive:0 强制卸载,下次全新加载——短期有效
- **分叉点 ⚡**:单模型直出 vs 两阶段(梗概→逐镜小步展开)→ **两阶段**,每步输出短
- **后话**:keep_alive:0 的高频加载/卸载是 M3 期 Ollama 劣化的元凶(见问题 11)

### 问题 7:Ollama×ComfyUI GPU 死锁
- **现象**:ComfyUI 空闲驻留 ~3.5GB 时,Ollama 加载 16GB 模型卡死(连 1+1 都无响应)
- **解法**:流水线内置排他切换,两应用不同时占卡

### 问题 8:成片拼接的缓存陷阱
- **现象**:重跑 concat 时复用了旧 clip 文件(内容已过期)
- **解法**:删旧 clip 重拼;后续给"0 字节文件"加防护删除

## M2:升级版(720p + 旁白)

### 问题 9:大动图转换爆内存
- **现象**:imageio.mimread 读 720p×121 帧动图超 256MB 保护上限
- **解法**:imageio 流式逐帧(get_reader/get_writer);ffmpeg 的 webp 解复用器不认动图(0 帧),勿用
- **知识**:0 字节残留文件会让"已存在跳过"逻辑静默复用坏文件

### 问题 10:旁白方案选型
- **分叉点 ⚡**:Windows SAPI(离线但机械音) vs edge-tts(需联网但神经音色+SSML)→ **edge-tts**
- **知识**:情绪标签→rate/pitch 映射表;[低沉]-15%/-2st、[激昂]+10%/+1st

## M3:制片流程化

### 问题 11:Ollama ROCm 反复加载/卸载劣化 ⭐ 复盘最大教训
- **现象**:M3 期剧本连续空响应/请求挂起,重启服务也只好一小会儿
- **根因**:keep_alive:0 策略(M1 期为了治 27B 空响应引入的)导致高频加载/卸载循环,把 ROCm 运行时磨坏
- **解法**:**常驻加载 keep_alive:"30m"**(实测 5/5 稳定)——"治上一个问题的药成了下一个病的因"
- **教训**:修复手段要定期复核,尤其涉及底层状态的

### 问题 12:Ollama 假死与重启姿势
- **现象**:服务假活(/api/ps 有响应,chat 全挂)
- **解法**:重启时**必须显式带三个环境变量**(OLLAMA_MODELS=F:\ollama、ROCBLAS_USE_HIPBLASLT=0、ROCBLAS_TENSILE_LIBPATH),否则不继承 setx 值
- **流程**:用户授权后 taskkill + 带 env 的 serve

### 问题 13:GPU 交接死锁
- **现象**:Ollama 模型卸载后起 ComfyUI,服务器进程活着但假死(端口无响应)
- **根因**:模型卸载不足以释放 ROCm 上下文,残留污染新进程初始化
- **解法**:**整进程停掉对方**(taskkill ollama.exe / ComfyUI PID),同一时间只有一个 HIP 应用
- **落地**:stop_ollama()/start_ollama() 与 stop_comfy()/start_comfy() 成对出现

### 问题 14:8B 模型吐空 JSON
- **现象**:llama3.1:8b 对复杂嵌套 schema(数组套对象)直接返回 `{}`
- **解法**:**扁平字符串 schema**(所有字段用字符串,场景列表用字符串数组)

### 问题 15:Lumen 复述原文
- **现象**:某镜草稿把整篇原文翻译成英文当"提示词"(10K 字符),还把"25字"指令抄进旁白
- **解法**:草稿校验(提示词≤600字/旁白≤80字超限重试)+ 追加"禁止复述原文"指令 + 链式上下文只保留最近 2 镜 + TTS 阶段杂质清理

### 问题 16:剧本质量问题(制片人反馈)
- **反馈**:剧本没内容没对话、人物表情动作缺失、战争紧迫感没体现、运镜单调
- **解法**:27B 改写升级为"创作级改写"——规则强制:对白/表情动作/紧迫感要素(敌军距离/时限/伤亡)/运镜不重复/情绪标签多样化;27B 调用加 think:false + num_predict 限幅
- **分叉点 ⚡**:润色(保结构小改) vs 创作级改写(显著提升)→ **创作级改写**

## 分叉点汇总(决策树速查)

| # | 分叉 | 选择 | 一句话理由 |
|---|---|---|---|
| 1 | H3 vs Wan 2.2 | Wan 2.2 5B | 16GB AMD 卡现实约束 |
| 2 | DirectML vs ROCm | ROCm | FP8/GGUF 刚需 |
| 3 | 单模型 vs 两阶段编剧 | 两阶段 | 短输出稳定 |
| 4 | 纯27B vs 纯14B vs 组合拳 | 组合拳 | 快慢搭配,扬长避短 |
| 5 | SAPI vs edge-tts | edge-tts | 神经音色+情绪控制 |
| 6 | 润色 vs 创作级改写 | 创作级改写 | 制片人对内容深度有要求 |
| 7 | keep_alive 0 vs 常驻 | 常驻 30m | 加载循环磨坏 ROCm |
| 8 | 卸载模型 vs 停进程交接 | 停进程 | 残留上下文挂死对方 |

## 通用教训

1. **这台机器的 ROCm 是所有 GPU 问题的交集**:二镜诅咒、Ollama 劣化、交接死锁、ComfyUI 假死——遇到"活进程无响应"先怀疑它
2. **断点续跑设计救了每一次翻车**:所有状态(剧本/镜头/资产)逐项落盘,重跑不重做
3. **修复要复核**:keep_alive:0 从"解药"变成"毒药"用了两天才暴露
4. **LLM 输出的防御式编程**:空响应、schema 漂移、复述原文、指令杂质——每种都要校验+重试+清理
5. **⭐ num_ctx 默认 2048 是隐藏杀手**(2026-10-17 破案):Ollama 请求不显式设 num_ctx 时,提示词一长(>1900 token)生成空间被挤爆——症状是输出在 ~92 token 处截断(done_reason: length)或请求直接 400。诊断方法:看 done_reason + eval_count,`prompt_eval + eval ≈ 2048` 即确诊。**修复:所有请求显式 num_ctx: 8192**。此根因同时解释了之前所有"神秘 400"
6. **ModelScope CDN 尾部坏块**(2026-10-17):SDXL 6.9GB 下载卡在最后 546KB——CDN 节点在固定字节偏移确定性截断(重试 N 次同位置断),尾段独立请求直接 0 字节。**规避:分段下载 + 坏块单独换源补**(hf-mirror 的 stabilityai 同款文件大小不一致会 416,需先核大小);整段重下前先停掉所有并发下载,避免 rm/append 竞态
